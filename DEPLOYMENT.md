# Hosting this for free

Three properties of this application decide which free platforms suit it, and
they are worth stating before the options:

1. **It is CPU bound.** One simulation is tens of thousands of Runge Kutta
   steps in Python. A request costs far more than serving a page does.
2. **The rate limiter holds state in memory.** It only means anything inside a
   single long lived process. Spread across serverless instances it still runs,
   but it stops being a control.
3. **The contact form writes to disk.** On a read-only or ephemeral filesystem
   that either fails or, worse, appears to succeed and loses the message.

The application handles the third itself: at start up it probes whether it has
somewhere durable to write, and if not the contact form is disabled with an
explanation rather than accepting messages it will drop.

## The options, compared honestly

| Platform | Fit | What you give up |
|---|---|---|
| **Render** free web service | Best match. A real gunicorn process, so the limiter and sessions work as written. No card needed. | Sleeps after 15 minutes idle; the next visitor waits roughly 30 to 60 seconds. 750 instance hours per month. Ephemeral disk. |
| **Hugging Face Spaces**, Docker | Good for a research demo, and the audience is the right one. Free CPU tier is 2 vCPU and 16 GB. | Sleeps when idle. Storage is ephemeral unless you pay. Public by default. |
| **PythonAnywhere** free | The only option here with a genuinely persistent filesystem, so the contact form actually works. | Free subdomain only, CPU seconds quota, and outbound internet is restricted, which this app does not need. |
| **Google Cloud Run** | Containerised, scales to zero, generous free allowance. | Needs a card on file even to stay inside the free tier. Ephemeral filesystem. |
| **Vercel** Hobby | Works, and the config is here, but it is the weakest fit of the five. | Read-only filesystem apart from `/tmp`; the rate limiter degrades to near useless; function duration is capped; Hobby is non-commercial use only. |

**Recommendation: Render.** It is the only free option whose shape matches how
the application is written, and it needs no card. Use Hugging Face Spaces
instead if you want it alongside the research audience, or PythonAnywhere if
the contact form mattering more than cold starts.

## Render

`render.yaml` is in the repository, so this is a blueprint deploy.

1. Push to GitHub, which is already done.
2. On Render, choose New, then Blueprint, and point it at the repository.
3. Set `AGGSIM_SITE_ORIGIN` to the URL Render gives you, for example
   `https://guidance-simulator.onrender.com`. Canonical links, Open Graph tags
   and the sitemap all read from it.

`AGGSIM_SECRET_KEY` is generated by Render, so sessions survive restarts.
The blueprint runs two workers and halves the configured rate limit to
compensate, because each worker keeps its own token bucket.

## Hugging Face Spaces, Cloud Run, Fly.io

All three take the `Dockerfile`.

```bash
docker build -t guidance-sim .
docker run -p 8080:8080 -e AGGSIM_SECRET_KEY=$(python3 -c "import secrets;print(secrets.token_urlsafe(48))") guidance-sim
```

For Spaces, create a Docker Space and push the repository. Set
`AGGSIM_SECRET_KEY` as a Space secret, not as a variable, so it is not shown in
the interface. The image runs as a non-root user and omits Matplotlib, which
the web path never imports.

## Vercel

`vercel.json` and `api/index.py` are here, so `vercel deploy` works. Read this
first, because three things behave differently:

- **The filesystem is read only** apart from `/tmp`. Contact messages have
  nowhere durable to go, so the form disables itself and says why. Setting
  `AGGSIM_MESSAGE_STORE=/tmp/messages.jsonl` would re-enable it, and the
  messages would then be lost whenever the instance recycles, which is why it
  is not the default.
- **The rate limiter cannot see other instances.** Each cold start begins with
  a full bucket, so a distributed client is barely limited at all. `api/index.py`
  tightens the numbers, but the honest answer is to put Vercel's own firewall
  or WAF rules in front of it.
- **Function duration is capped.** The Hobby limit has moved recently, from ten
  seconds toward sixty on newer deployments, so check the current
  [function limits](https://vercel.com/docs/functions/limitations). `api/index.py`
  lowers `AGGSIM_MAX_SIMULATION_STEPS` to 12,000 so a long run finishes inside
  the smaller of those figures rather than returning a gateway timeout.

Hobby is also licensed for non-commercial use only.

## The option that removes the problem

Every constraint above exists because the simulation runs on a server. It does
not have to. The model is a few hundred lines of arithmetic with no
dependencies beyond array maths, so it could be ported to run in the visitor's
browser and served as static files from GitHub Pages, Netlify or Cloudflare
Pages.

That would mean no server, no cold starts, no rate limiting to reason about, no
personal data leaving the browser, and no hosting cost that can ever be
exceeded. The cost is a real port of the integrator, the controllers and the
implement kinematics to JavaScript, plus a second implementation to keep in
step with the Python one. It is the right answer if this becomes something
people are pointed at often, and the wrong one while it is still changing.

## Before any public deployment

- Set `AGGSIM_SECRET_KEY`. Without it each process invents its own, and with
  more than one worker the contact form fails its CSRF check.
- Set `AGGSIM_SITE_ORIGIN` to the real URL.
- If you are behind a proxy or CDN, add `ProxyFix` with the correct hop count,
  or the rate limiter sees only the proxy address and treats every visitor as
  one client.
- Run `python3 scripts/security_audit.py` and read the warnings.
